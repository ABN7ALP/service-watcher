# البند 5 من مراجعة PR #102 — إثبات بخادم حي فعلي

هذا المجلد يوثّق تنفيذ البند 5 من جدول "مراجعة PR — الجولة الثانية" في وصف هذا الـ PR،
بعد توسيع سياسة شبكة الجلسة للسماح بـ`fastdl.mongodb.org`/`repo.mongodb.org`. الجولة
السابقة وثّقت استحالة هذا البند بسبب حجب هذين النطاقين (راجع الصف القديم في جدول
المراجعة)؛ هذي المحاولة أعادت التنفيذ **بخادم Express/Socket.IO حقيقي** متصل
بـ`mongodb-memory-server` بوضع **replica set** (معاملات/transactions حقيقية كالإنتاج)،
لا أي محاكاة أو mock.

## المنهجية

- **الخادم**: نفس `server/server.js` حرفياً، يعمل كعملية Node منفصلة (قابلة للقتل وإعادة
  التشغيل فعلياً)، متصلاً بـ`MongoMemoryReplSet` حقيقي (ثنائي `mongod` حقيقي نزّل فعلياً
  بعد توسعة الشبكة).
- **المتصفح**: Chromium حقيقي (Playwright) يحمّل `public/index.html`/`app.js`/
  `public/dist/style.css` الحقيقيين — نفس الملفات المبنية فعلياً، لا نسخة مصغّرة منفصلة.
  تسجيل الدخول عبر تخزين `token`/`user` بـ`localStorage` تماماً كما يفعله `login.js`
  الحقيقي بعد نجاح `/api/auth/login`، ثم إعادة تحميل الصفحة — لا حقن DOM مباشر.
- **التفاعل**: كل خطوة متعلّقة بالميزة قيد المراجعة (دخول الغرفة، إنشاء/قبول تحدي
  المقاعد، تحدي PK بين الغرف، إرسال الهدايا الداعمة) تمّت بضغط عناصر الواجهة الحقيقية
  فعلياً (لا استدعاء socket مباشر من السكربت). إنشاء الحسابات السبعة التجريبية والغرفتين
  تمّ عبر مسارات الخادم الحقيقية (`/api/auth/login`, `/api/voice-room/rooms`) من سكربت
  تنسيق خارجي — فقط إنشاء المستخدمين أنفسهم تمّ مباشرة عبر Mongoose (نفس `User.create`
  بكل خطافاته) لتفادي محدد معدّل التسجيل (5 حسابات/ساعة لكل IP)، وهذا مسار غير متعلّق
  بالميزة قيد المراجعة أصلاً.
- **مكتبات CDN محجوبة بالبيئة** (`cdn.socket.io`, `cdn.jsdelivr.net`, إلخ): هذه
  المكتبات (socket.io-client, confetti, qrcode, chart.js, cropper.js) نُزّلت من سجل npm
  (متاح بالبيئة) وخُدمت محلياً عبر `/vendor/*` فقط أثناء هذا الاختبار — تعديل مؤقّت على
  `public/index.html` أُعيد بالكامل لحالته الأصلية بعد الاختبار ولم يُدفع بأي شكل.
- **صور خارجية مكسورة بالبيئة فقط**: `res.cloudinary.com`/`images.unsplash.com` محجوبان
  بسياسة الشبكة هنا، فصور الأغلفة/الهدايا تظهر كأيقونة صورة مكسورة باللقطات — تجميلي بحت،
  لا علاقة له بمنطق PK/تحدي المقاعد قيد المراجعة (التاج `crown_3d.webp` وكل أصول PK
  الحقيقية محليّة بـ`/assets` وتظهر سليمة).
- **"مدة 60 ثانية" لمعركة PK بين الغرفتين**: التحدي أُنشئ فعلياً بأقصر مدة إنتاجية متاحة
  بالواجهة (180 ثانية — نفس enum الخادم الحقيقي `[180,300,600]`، لا قيمة مختَرَعة). بعد
  تفعيله فعلياً بالقبول الحقيقي من الطرفين، عُدِّل فقط حقلا `startedAt`/`endsAt` بالمستند
  مباشرة (لا `durationSeconds`، ولا أي لمسة لمنطق التفعيل/التسوية/الإنهاء نفسه) لضغط
  النافذة الزمنية المتبقية لـ60 ثانية حقيقية بالضبط — طريقة قياسية لضغط زمن اختبار دون أي
  تعديل على الكود أو المنطق المُختبَر.

وسط معركة PK فعلية بين غرفتين، وأُعيد تشغيله كعملية جديدة بالكامل (فَقَدت كل المؤقّتات
بالذاكرة) قبل 10 ثوانٍ بالضبط من موعد انتهاء المعركة. رغم ذلك، النتيجة وصلت لكلا الطرفين
بعد ~11.5 ثانية من الموعد المفترض، فقط بفضل المكنسة الدورية (بند 2 بالمراجعة) — تماماً
كما صُمم الإصلاح.

## نتيجة فحص قاعدة البيانات (إثبات تطبيق نقاط الدوري مرة واحدة فقط)

```
battle.status = ended
battle.lpSettled = true
battle.winner = B
غرفة A: lp=50   appliedBattleIds يحوي معرّف هذي المعركة بالضبط مرة واحدة (1)
غرفة B: lp=300  appliedBattleIds يحوي معرّف هذي المعركة بالضبط مرة واحدة (1)
✅ IDEMPOTENCY CHECK PASSED — النقاط طُبّقت مرة واحدة فقط لكل غرفة (لا ازدواج رغم القتل/التسوية المتأخرة)
```

هذا الفحص استُخرج مباشرة من مستندي `PkStanding` الحقيقيين بقاعدة البيانات الحيّة بعد
انتهاء السيناريو — وليس افتراضاً.
