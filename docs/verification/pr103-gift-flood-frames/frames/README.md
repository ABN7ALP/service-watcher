# البند 8-11 — توحيد نظام إطارات الصور: إثبات بخادم حي فعلي

نفس المنهجية المستخدَمة بمراجعة PR #102 (`docs/verification/pr102-item5/`): خادم
`server/server.js` الحقيقي كعملية Node منفصلة متصلة بـ`MongoMemoryReplSet` حقيقي (معاملات
حقيقية)، ومتصفح Chromium حقيقي (Playwright) يحمّل `public/index.html`/`app.js`/
`public/dist/style.css` المبنيّين فعلياً — تسجيل دخول حقيقي (JWT + مستند مستخدم كامل
بـ`localStorage`، تماماً كمسار `/api/auth/login` الحقيقي)، وكل تنقّل بالواجهة عبر نقر عناصر
حقيقية (بحث عن الغرفة بالاسم ← نقر البطاقة، ⋯ ← الإعدادات ← متجر الإطارات...).

## البذر (هذي الجولة — بعد استبدال الأصول الحقيقية)

21 مستخدماً — `activeFrameClass` مضبوط ذرّياً عبر Mongoose مباشرة (بلا حاجة لمسار الشراء
لإثبات العرض نفسه)، ضمن خادم Express/Socket.IO حقيقي متصل بـ`mongodb-memory-server`
(replica set) حقيقي بالكامل:

- **غرفة 9 مقاعد** (`مراجعة PR103 - غرفة 9`): المضيف (`pr103r9host`، luxury-01) + 8 مستخدمين
  على المقاعد 2-9 بالإطارات القابلة للشراء الثمانية الأخرى — تسعة أصناف مختلفة بالضبط على
  تسعة مقاعد.
- **غرفة 19 مقعداً** (`مراجعة PR103 - غرفة 19`): مضيف مستقل (`pr103r19host`، luxury-01) +
  10 مستخدمين على المقاعد 2-11 (الثمانية الأخرى القابلة للشراء + المساهم + الأدمن) =
  **الإطارات الـ11 كاملة معاً**، بالمقاعد 12-19 فارغة.
- **الملف الشخصي**: `pr103director` (`isAdmin:true`، إطاره النشط pegasus-warrior) — تسجيل
  دخول حقيقي عبر `/api/auth/login` (JWT + مستند مستخدم كامل بـ`localStorage`، تماماً كمسار
  `login.js` الحقيقي)، ثم مسار واجهة حقيقي بعرض الهاتف: زر "المزيد" بالشريط السفلي ← "ملفي
  الشخصي". دخول الغرفتين كان عبر "الرجوع للبث" (كل مضيف يفتح نافذة "بثّك لسا شغّال" تلقائياً
  لأن بثّه مُعرَّف حيّاً منذ البذر) — يدخل غرفته الحقيقية بنفس `enterVoiceRoom()` التي يستخدمها
  نقر بطاقة غرفة عادية.
- مكتبات CDN محجوبة بسياسة شبكة هذي الجلسة تحديداً (`cdn.socket.io`, `cdn.jsdelivr.net`):
  استُبدلت مؤقتاً بنسخها الحقيقية من سجل npm مخدومة محلياً عبر `/vendor/*` أثناء هذا الاختبار
  فقط (نفس أسلوب `docs/verification/pr102-item5/`) — `public/index.html` أُعيد بالكامل
  لحالته الأصلية (روابط CDN) بعد الاختبار ولم يُدفع أي تعديل عليه.

## أصول الإطارات

🛡️ **تحديث مراجعة لاحقة**: الجولة الأولى من هذا الفرع كانت ولّدت 11 أصلاً بديلاً اصطناعياً
(`scripts/generate-placeholder-frames.js`، مربعات ملوّنة بفتحة دائرية بلا أي فنّ حقيقي) بسبب
حجب شبكي لـ`res.cloudinary.com` بجلسة التطوير حينها — **هذا كان خطأً جسيماً تقريباً دُمِج
بالخطأ** (كان سيستبدل إطارات المستخدمين المدفوعة الحقيقية بمربعات بلا أي زخرفة). الشبكة
مفتوحة الآن: `node scripts/normalize-frames.js` نُفِّذ فعلياً ضد روابط Cloudinary الـ11
الحقيقية (نفسها بـ`IMAGE_OVERLAY_FRAMES` السابقة)، `scripts/generate-placeholder-frames.js`
حُذف نهائياً من الفرع، ولا أثر لأي بديل اصطناعي بـ`public/assets/frames/` بعد الآن. راجع
`selftest-output.txt` لإثبات صحة خوارزمية التوحيد نفسها (5/5 حالات اصطناعية، بما فيها مصدر
متحرك) — منفصل تماماً عن الأصول الحقيقية الموثَّقة هنا.

**تصحيح يدوي واحد** (`scripts/frames-manifest.json`): إطار `lion-bee-sapphire` فيه وجه أسد
وجناح نحلة يبرزان فعلياً داخل حدود الفتحة (لا على محيطها فقط كبقية الإطارات)، فكان الاكتشاف
الآلي (مسح شعاعي 8 اتجاهات + وسيط) يلتقط نصف قطر أكبر من اللازم ويقصّهما عند التحجيم — راجع
`lion-bee-sapphire-before-after.png` بمجلد `checkerboard/` أدناه. التصحيح نصف قطر ثابت مُقاس
يدوياً من لقطة تشخيص (دائرة الاكتشاف فوق خلفية شطرنجية)، يُستخدَم فقط داخل normalize-frames.js
وقت التوحيد — بلا أي أثر على مكوّن `.avatar` بـapp.js أو CSS (القاعدة هناك ثابتة 160% بلا
استثناء لكل الإطارات الـ11، بما فيها هذا). بقية الإطارات الـ10 فُحصت بصرياً فرداً فرداً (دائرة
الاكتشاف الآلي فوق خلفية شطرنجية لكل واحد) واعتُمد الاكتشاف الآلي بلا أي تصحيح — راجع
`checkerboard/` لنتيجة كل واحد منها.

## ميزانية الحجم (<400KB/ملف) — الحركة لا تزال حقيقية

أول تشغيل لـ`normalize-frames.js` ضد الأصول الحقيقية أنتج ملفات 3-10MB (الأصول المتحركة
بجودة 88 وكل لقطاتها الـ40-100 الأصلية) — أبعد ما يكون عن ميزانية 400KB. الحل (راجع تعليق
`MAX_ANIMATED_FRAMES` بالسكربت): عيّنة ثابتة المسافة من اللقطات (10 كحد أقصى لا كلها — كافية
بصرياً لتأثيرات البريق/التوهج البطيئة بهذي الإطارات) + جودة WebP أخفض للمتحرك تحديداً
(quality=28, alphaQuality=32, effort=6 — الثابت وحيد اللقطة يبقى 88). فحص صارم بعد كل ترميز
يرمي خطأً واضحاً لو تجاوز الناتج 400KB بدل شحنه بصمت.

## البند 10 — ثبات الحجم عبر تغيّر الإطار (مُثبَت حيّاً)

مستخدم جالس فعلياً بالمقعد 2 بغرفة 19 (royal-01 من البذر) — بثلاث عمليات REST حقيقية
متتالية (`POST /api/frames/equip` بـ`frameId:null` للإزالة، ثم `POST /api/frames/purchase`
+ `equip` لإطار fire-dragons، ثم نفس الشيء لـluxury-01)، بينما متصفح **متفرّج آخر حقيقي**
داخل نفس الغرفة يستلم `user-frame-changed` حيّاً ويُقاس `getBoundingClientRect()` على صورته
بالمقعد بعد كل خطوة:

| الحالة | العرض×الارتفاع | يحمل إطاراً؟ |
|---|---|---|
| ابتدائي (royal-01) | 36×36px | نعم |
| بعد الإزالة | 36×36px | لا |
| بعد الإضافة (fire-dragons) | 36×36px | نعم |
| بعد التبديل (luxury-01) | 36×36px | نعم |

**36px ثابتة بكل الحالات الأربع — `applyFrameChangeByUserId`/`applyFrameToAvatarWrap` يلمسان
`.avatar__frame` فقط، لا يغيّران حجم الصورة إطلاقاً.** راجع `size-consistency-final.png`.
